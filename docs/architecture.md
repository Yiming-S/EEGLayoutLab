# Architecture

EEGLayoutLab is a browser application served by a local Python service, `eeglayoutlab serve`, which runs bounded Python workers for one workspace. The web application is maintained; the native Mac wrapper and packaging tools have been retired. The macOS scientific runtime remains available for local browser use.

This page describes the current structure. The move to a local-first application, in stages that keep results and cache keys valid, is described in [design 0001](design/0001-local-first-architecture.md); its phase 2 replaced the Node HTTP host with the Python service ([phase 2 results](design/0001-phase-2-plan.md#phase-2-results)). The Node host stays in `webapp/server/` as a legacy host until phase 4, and hosted deployments stay at the tag `node-host-freeze`.

## Module boundaries

```text
app route -> feature workspace/controller -> client/task-client
          -> eeglayoutlab serve -> durable workspace FIFO + execution slot
          -> Python worker -> compact_eeg workflow -> verified record
```

Browser modules do not import server implementations. Server imports are checked for cycles. Shared layout contracts have no renderer dependency. Request fixtures exercise the existing Node and Python validators. The design-evaluation, coordinate-source, radius-search, electrode-editor, source-reception, robustness-study and research-project formats are also defined in `eeglayoutlab.schemas`, checked against the Node normalizers, and the interface's types for them are generated from those definitions ([contracts](../contracts/README.md#generated-request-types)). The other formats are not yet ported ([design 0001](design/0001-local-first-architecture.md), phase 1). See [API formats](../contracts/api-formats.md).

The viewer's asset loader validates atlas groups and hashes before use. A scene lifetime owns generated geometry, materials, labels, event listeners, observers and the renderer. `lib/anatomical-head-scene.ts` preserves the existing exports. Reception separates pure result projections, one shared playback timeline and paired receiver panels; display controls do not recalculate scientific scores.

Viewer instances share downloads and SHA-256 validation through `viewer/asset-cache.ts`. The cache retains at most 32 MiB and four verified binary entries, keyed by URL and checksum. Each scene receives its own position, normal and index arrays and can dispose them independently. Aborting one viewer does not cancel another viewer's download; the underlying request is canceled when its last subscriber leaves. Failed requests are removed so the next load can retry. Model indexes are revalidated on each mount, and binary URLs include their checksums so a deployment can replace a model without reusing the previous version's browser cache.

Reception loads each 3D module when its placeholder comes within 200 px of the viewport. Once activated, scrolling away preserves the camera and selection. A manual load control and an observer-free fallback cover other browsers. Playback stops its interval while the document is hidden and resumes at the saved position only if playback was already active.

## Execution and records

The Python service runs every computation for one local user ([phase 2 plan](design/0001-phase-2-plan.md), slices 4 to 7). The worker runner handles progress output, output limits, cancellation, timeout and process-tree termination. A permit remains held until process closure, result validation and persistence finish. Cache lookup remains available without occupying that permit. `eeglayoutlab.jobs.queue` keeps the receipts of a workspace in `<workspace>/.eeglayoutlab/queue.json`. `jobs.worker` and `jobs.slot` run the workers and hold the permit. While a worker runs, the permit also holds an installation-wide lock, `results/v2/.eeglayoutlab-execution.lock`, so two workspaces of one checkout compute one at a time. `jobs.records` writes the records with Node's bytes and publishes a `cache.json` once, never replacing a valid one. The radius search (slice 4), the coordinate evaluation (slice 5), the electrode editor (slice 6) and the signal simulation, v1 and v2 (slice 7), run there; `eeglayoutlab serve --cache-only` serves stored results and refuses new work. An electrode edit starts from a layout of the library, and the digest of that layout's library record enters the edit's key, so an evaluation whose parent has changed since it was prepared is refused. The electrode names and source declaration imported with coordinates never enter a request or its key: they are an annotation of the workspace, `<workspace>/annotations/electrode-names/<id>.json`, written once, which the task receipt references and which job views, library records and bundles show for `?annotation_id`. The library also reads the annotations the Node host wrote under `results/v2/design_evaluation_jobs/electrode_annotations/`. A v2 signal simulation's key includes the digest of the numerical runtime, which the reception inspector prints in a subprocess of the native interpreter (`jobs.runtime_digest`, memoized while the files it watched are unchanged); the service never computes it in-process. The completed signal simulations of a workspace are its signal records (`/api/community/records`), and each record's original result is read back as it was saved, checked against its saved layout rather than the current identity. A robustness study (slice 8) is a list of 1 to 12 coordinate evaluations of one design; it is stored in the workspace, `<workspace>/studies/<id>/study.json`, with a copy of each completed case's original `cache.json` bytes under `snapshots/`, so a study keeps its results after the receipt or the record is gone. Opening a study never submits work: its cases are submitted one at a time after an explicit start, one study runs at a time, and after a restart a running study waits for an explicit resume. A research project (slice 9) is stored the same way, `<workspace>/projects/<id>/project.json`, with each saved result's frozen copy under `snapshots/`; its delivery is built from those copies alone.

The legacy Node host's `community-queue.mjs` stores anonymous task receipts and FIFO order in its queue directory, and its four scientific services share `jobs/execution-slot.mjs`. Both hosts write the same records under `results/v2`; do not compute on both at once.

Radius design and in-bank editing read the frozen lead-field bank. Fixed-coordinate evaluation retains its existing `1e-7 mm` bank/reference matching checks; other qualified coordinates require native FEM, or the published scalp-node table described below. Reception reuses bank fields only at exactly identical saved coordinates. Editor and V2 reception initialization also validate native inputs and runtime identity, so a bank-backed operation alone does not establish that a minimal Python environment supports the full application.

Native coordinate evaluation also prepares reception fields using the same model instance, source operator and factorization. It preserves the original design and reception projection paths separately: repeated projection can change floating-point coordinates, so design fields are not substituted for reception fields. The verified reception matrix and QA are published atomically under `results/v2/reception_forward/shared_fields/`, keyed by exact coordinates, model/source inputs, code, runtime and thread settings. Reception still requires a valid completed design record. A failed optional preparation leaves the successful design available; identity changes, corrupt archives and cancellation remain errors. Old reception archives remain readable.

When `results/v2/current_scalp_node_table.json` exists, coordinate evaluation of non-bank points reads a precomputed scalp-node table instead of factorizing the head model. `scripts/build_scalp_node_table.py` solves, once, a unit load at every table vertex against the fixed gauge node, using the qualified MUMPS path and the same residual/current thresholds as a direct solve. The table vertices are every vertex of an exterior triangle whose three vertices pass the current surface admissibility mask, plus every admitted bank candidate vertex. An admitted candidate can sit on a vertex whose incident triangles all touch a screened vertex; its zero-weight corners are redirected to that vertex. On Ernie this adds vertex 46112, read by bank candidate 4925, for 40,024 vertices. A point electrode's load is the barycentric combination of its triangle's three node loads, so its row is the same combination of node rows: superposition of one linear operator, not interpolation between electrodes. Evaluation keeps the original cortech projection, reads three SHA256-checked rows per electrode and must reproduce the bank reference within `1e-8`. The table is bound to the bank, candidate geometry, source inputs, head hashes, admission mask and vertex rule; any difference is an error, never a fallback to direct FEM, until the table is rebuilt. Because the vertex rule is part of the table identity, the nominal table and both conductivity-scenario tables built under the earlier rule must be rebuilt. Its pointer, manifest, index and row bytes enter the shared cache identity. Results record `forward_mode: scalp_node_table` and the table ID. Reception for such a design uses the same table and fails if it has been replaced; designs evaluated with direct FEM keep their native reception path.

The service reuses a reception runtime identity only while its observed filesystem state remains unchanged (`jobs.runtime_digest`, a port of the Node host's `runtime/identity-cache.mjs`). The Python snapshot wrapper retains the original runtime digest algorithm and records files, directories, import paths, launchers and symlink targets. The memo rechecks inode/device, type, size, nanosecond modification/change times and executable mode, coalesces pending checks and evicts failed entries. An older scientific checkout without the snapshot wrapper uses the original uncached inspection. This optimization does not change scientific cache keys.

## Research projects

Projects keep annotations and immutable scientific copies in the workspace, `<workspace>/projects/`, for its one local user ([phase 2 plan](design/0001-phase-2-plan.md), slices 9 and 10): no credential is stored or checked, `GET /api/projects` lists the workspace's projects, the project page opens them from that list or from `/projects?project=<id>`, and sharing is not an endpoint. Owner names are descriptive metadata rather than authenticated accounts. The bytes of `project.json` and of every snapshot, the revisions, the size bounds and the deliveries are the Node host's; a delivery's host metadata names the Python service's files.

The legacy Node host keeps projects under `<queue directory>/projects/`, behind owner and revocable viewer credentials hashed on the server, which the current interface no longer sends. `eeglayoutlab workspace import-legacy` copies the projects, robustness studies and completed signal records it saved under its queue directory into a workspace, after the checks its stores make when they read them; it only reads the queue directory.

Attaching an entry resolves a validated completed layout, editor evaluation or completed signal task of the workspace on the server. It saves a checksummed copy of the full scientific payload. Project annotations, selected reference/candidate layouts and comparison requirements remain separate from scientific requests and identities. Optimistic project revisions prevent stale writes. Receipt pruning and cleanup of the original calculation cache do not erase these saved copies. Recognized temporary files left by interrupted atomic snapshot writes are retained and counted in storage limits, never read as completed science.

The browser retains the active project per tab and provides explicit save actions in existing tools. Archived result views read project snapshots directly. Scientific delivery bundles keep exact snapshot text, a checksum manifest, annotations, comparison settings and copied original readings. Current export-host fingerprints are separate from the original calculation identities. Delivery preparation is bounded and does not start scientific work. See [project formats](../contracts/project-formats.md).

## Local operations and admission

This section describes the legacy Node host; the Python service has none of it, being local to one user (design 0001, phase 2, "Not carried over"), and its `--cache-only` replaces the maintenance mode. The Node host's outer HTTP observer generates request identifiers, correlates returned task IDs and writes bounded private logs containing route labels, status and duration. It does not log credentials, query strings, scientific inputs or response payloads. The local operator status endpoint requires a direct loopback request without browser or proxy metadata; the computation token does not grant operator access.

Filesystem free-space checks and an optional current Node RSS threshold apply before accepting uncached work, before dispatch and before project mutations. Cache lookup, existing results and cancellation remain available. Resource-blocked tasks retain their FIFO position. These operational settings do not enter scientific cache identities or change worker thread counts. Current Node memory is not scientific-worker peak memory or a hard OS resource limit. Accepted project writes and pending operational logs are flushed before releasing the queue owner during shutdown.

## Host checkout and scientific root

The **scientific root** contains worker scripts, `src/`, scientific configurations, installed model inputs, generated records and the managed runtime. `eeglayoutlab serve` takes it from `--root` or `EEG_REPOSITORY_ROOT`, by default the checkout the command was installed from, and serves that root's built interface (`webapp/dist/client`, or `--static`). The **workspace** holds the user's queue, annotations, studies and projects. The legacy Node host's **host checkout** supplies `webapp/`, dependencies and the production build, `EEG_REPOSITORY_ROOT` selects its scientific root, and `EEG_QUEUE_DIRECTORY` can place its queue state elsewhere; its value must be absolute.

The store preserves existing paths:

- `results/v2/local_app_jobs/`, `design_evaluation_jobs/`, `electrode_editor_jobs/`, `source_reception_jobs/` and `source_reception_v2_jobs/` contain generated job records.
- `results/v2/reception_forward/` contains generated forward fields.
- `results/web-service/` is the legacy Node host's default queue, signing-secret and operational-log directory; the Python service never writes it.
- Other paths named in `data/manifest.json` remain frozen inputs or supplied records, including entries under `results/v2/`.

This configuration supports a new host checkout using an existing scientific snapshot. It does not move data, rewrite old records or introduce independently relocatable input/result roots. A release manifest verifies that the scientific source expected by the host matches the selected scientific checkout.

`EEG_COMPUTE_PYTHON` selects the ordinary worker interpreter. Native services retain their existing precedence: the scientific root's `.runtime/simnibs-4.6.0/bin/python` is preferred when present. Release checks record the interpreter actually selected.

## Compatibility and hosting

API JSON responses carry `X-EEG-API-Version: 1`; errors retain `error` and add a stable coarse `code`. Existing routes and scientific cache-key formats remain unchanged. Legacy Python entry points and Node compatibility exports remain part of the supported execution/import paths.

The Python service sends every response with identity encoding. The legacy Node host uses asynchronous Brotli/gzip streams for API JSON when accepted, with identity fallback and `Vary: Accept-Encoding`, and serves the `.br`/`.gz` variants of binary models that `npm run build` writes to `dist/client/models/`. Original model files and decoded JSON bytes are the same on both.

Cache identities include actual code, inputs and, where applicable, runtime bytes and filesystem paths. A changed path or environment can require a new calculation. Historical results retain their original identity; no approximate-coordinate cache fallback or hash rewriting is introduced.

The service listens on `127.0.0.1` only. Every request needs the session cookie that the command's launch link sets, and writes also need the token from health; a tab from an earlier run reaches no service (each start takes a new port) or gets 401 (a restart on the same port), and the interface asks to run the command again: every request goes through `client/task-client.ts` (`apiJson` or `apiFetch`), which tells the task menu at once, and the menu shows the advice at the foot of the window. The legacy Node host also listens on `127.0.0.1`; its explicit HTTPS-origin and trusted-proxy configuration enables the tested proxy policy and Secure cookies for a hosted deployment, which stays at the tag `node-host-freeze`. See [deployment](server-deployment.md), [queue behavior](anonymous-queue.md), [operations](web-operations.md) and [verification commands](../CONTRIBUTING.md).
